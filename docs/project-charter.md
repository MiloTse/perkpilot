## 1. 背景与动机

### 1.1 行业与经验背景

- **CLRP**（银行内部权益管理平台，原服务场景为**单一法人机构**内的权益配置、审批、生效与运营）提供了可复用的领域模型：活动/权益生命周期、**经办—复核—终审**、草稿与正式数据分离、同步接口与异步批量、报表与大数据处理等。
- **PerkPilot** 将同一类能力**产品化**为 **SaaS 型多租户权益管理云**：面向**多家金融机构**（或其他持牌/类金融客户）分别提供隔离的租户空间，在统一技术栈与交付链上持续迭代。

### 1.2 要解决的核心问题

- 多个法人机构在同一平台管理**权益白名单、权益卡包、活动/权益配置**，并支持 **CRUD、批量导入/导出、报告生成** 与可审计的审批链路。
- 在**数据、权限、密钥与可观测性**上满足多租户隔离与商业化交付的最低标准，并适配 **AWS** 上的运行与 **CI/CD**。

---

## 2. 项目定位与目标

### 2.1 一句话定位

**PerkPilot：面向多家金融机构的多租户权益与营销运营平台；租户内保留「总行/分行/终审」类审批与运营能力，平台侧提供统一身份、隔离数据与可重复发布工程。**

### 2.2 目标（可验收）

| 维度 | 目标（初版可裁剪） |
|------|-------------------|
| 多租户 | 每租户数据与配置边界清晰；默认禁止跨租户访问 |
| 身份与权限 | 租户内 RBAC；与统一认证方案集成（实现阶段在架构文档中定稿） |
| 业务能力 | 权益白名单、卡包、配置类 CRUD；批量任务与状态查询；报表/导出 |
| 工程化 | 主线 **CI/CD**；环境分层（如 dev / staging / prod）；版本语义化 |
| 合规叙事 | 审计日志字段、密钥与凭据不进入代码库；区域与数据驻留策略在架构中阐述 |

## 3. 术语与租户模型

### 3.1 租户（Tenant）

- **租户** = 一家**独立的金融机构或签约主体**（示例：**TD Bank**、**BMO** 作为两个租户；仅为说明，无商业关联）。
- 租户是 **计费、数据隔离、审计边界** 的根。

### 3.2 租户账号与登录用户

- **租户空间**：机构注册后获得独立租户标识（`tenant_id` / slug 等，技术定稿见数据设计文档）。
- **租户根管理 / 组织入口**：机构在平台创建的管理边界（口语中可称「TD 管理账号」等），在实现上应区分 **租户实体** 与 **自然人用户账号**，避免混用为同一概念。
- **登录用户**：隶属于某一租户（或平台运营方），持角色与权限。

### 3.3 与 CLRP 的关系（概念对照）

| CLRP（单法人行内） | PerkPilot（多法人 SaaS） |
|--------------------|---------------------------|
| 单一银行组织树 | 每租户一套组织与流程模板 |
| 行内角色命名 | 租户内可配置角色；产品侧推荐使用**带组织含义**的命名（见下节） |

> 注：CLRP 工程级回忆见本地 **`CLRP.MD`**（git 忽略）；立项书不展开行内专有实现细节。

## 4. 用户与角色（RBAC 概念）

### 4.1 原则

- **禁止**单独使用易歧义的「一级复核 / 二级复核」作为主角色名；审批顺序用 **分行复核 → 总行复核 → 终审** 或明确的 **L1/L2/L3** 映射表表达。
- **「一级」在 CLRP 语境中曾用于「分行一级经办」**，指**经办层级**，不等价于「第一级复核」。

### 4.2 推荐角色清单（租户内）

| 角色（中文） | 英文/代码建议 | 职责摘要 |
|--------------|----------------|----------|
| 租户系统管理员 | `TENANT_SYSTEM_ADMIN` | 本租户用户/角色/集成参数、流程模板绑定等 |
| 总行经办 | `HQ_OPERATOR` | 权益与活动配置发起；页面或导入表提交 |
| 总行复核 | `HQ_REVIEWER` | 复核总行经办提交 |
| 分行经办 | `BRANCH_OPERATOR` | 可选；启用「分行链」时出现 |
| 分行复核 | `BRANCH_REVIEWER` | 分行侧复核（**不推荐**命名为「一级复核」） |
| 终审 | `FINAL_APPROVER` | 终审通过后进入生效/异步处理（与实现态一致） |

面向国际机构时，**UI 文案**可采用 **Branch / HQ / Final**，与中文角色做映射。

### 4.3 审批链路（模板）

**模板 A — 仅总行**

`总行经办 → 总行复核 → 终审 →（生效：同步 API 或异步管道）`

**模板 B — 分行 + 总行**

`分行经办 → 分行复核 → 总行复核 → 终审 →（生效）`

具体状态机、草稿表与正式表策略见 **《系统设计》** 定稿。

## 5. 核心业务链路（产品级）

- **配置管理**：权益白名单、权益卡包、活动/权益的增删改查。
- **批量处理**：批量上传；异步任务；进度查询；完成后结果下载。
- **报表与导出**：周期性或按需报告；大体积导出与批处理策略在架构/数据文档中约束。
- **审计**：关键操作带 `tenant_id`、操作者、对象与时间戳（字段级策略待定）。

---

## 6. 范围说明

### 6.1 In Scope（初版倾向）

- 多租户 **B 端运营后台**（优先）；C 端持卡体验可作为后续迭代。
- 身份、租户上下文、RBAC、核心业务 API、持久化与基础可观测性。
- **CI/CD** 与至少一个可演示环境。

### 6.2 Out of Scope（除非另行立项）

- 单租户内的**核心银行账务/清算**全量对接（可作为外部系统边界）。
- 完整监管报送套件（可在架构中预留扩展点）。

---

## 7. 非功能需求（摘要）

- **安全**：最小权限；密钥与连接串不进仓库；租户强制隔离。
- **可用性**：单区域 MVP 可接受；生产路径在架构文档中定义 SLA 目标。
- **合规**：个人数据最小化、日志脱敏、数据驻留（尤其多地域金融机构）在架构评审中补充。

## 8. 技术栈与部署（摘要）

### 8.1 前后端分离与首屏形态

- **前后端分离**：浏览器 **SPA** 与后端 **API** 独立仓库或独立构建产物；首阶段交付 **网页端**（桌面浏览器优先）。
- **前端（主流技术）**：**TypeScript + React**，UI **MUI**，状态 **Redux Toolkit**；与后端通过 **HTTPS + REST（JSON）** 集成（契约见 API 文档）。

### 8.2 后端与集成

- **语言与构建**：**Java 21**（LTS）；**Maven**。
- **框架**：**Spring Boot 3.x**、**Spring Security**、（可选）**Spring Session Redis**。
- **持久层（已定稿）**：**MyBatis-Plus**；复杂 SQL、多表关联以 **Mapper XML** 为主，与 CLRP 实践一致。教学阶段掌握的 **Spring Data JPA** 不作为本仓库首版持久技术选型，以避免 **JPA + MyBatis** 双栈并存带来的复杂度（简单 CRUD 亦统一在 MyBatis-Plus 内实现）。
- **数据库迁移（已定稿）**：**Flyway**（详见 **`docs/data/database-design.md`**）。
- **批处理（已定方向）**：**Spring Batch**（Java）+ **Kafka** 异步管道；批量上传与重处理逻辑首版 **不引入 Python** 运行时。
- **消息与集成**：**Apache Kafka**（批量任务、进度/状态事件与领域事件；分区键建议含 `tenant_id`；主题与消费者组详见 **`docs/architecture/system-design.md`**）。
- **服务与消息边界（已定方向）**：服务间 **RESTful HTTP + JSON**；**Apache Kafka** 用于 **领域事件与批量管道**，不作为通用 RPC 总线（见 **`docs/architecture/system-design.md`**）。

### 8.3 数据库与可移植性

- **关系型数据库**：**PostgreSQL** 为开发与本地默认；云上目标形态为 **Amazon Aurora PostgreSQL**（与 PostgreSQL 协议兼容）。连接与 profile **通过配置切换**，不在代码中写死主机，便于「先本地跑通框架，再切云」。

### 8.4 容器化与运行形态

- **是否全面容器化（Docker / Compose / 云上编排）**：**讨论中**；本地可优先「能跑」再逐步统一为 Compose 或云镜像（见 **`docs/engineering/release-and-cicd.md`**）。

### 8.5 云与工程

- **AWS**：身份、网络、数据、对象存储、观测、流水线等（映射见系统设计）。
- **CI/CD**：见 `docs/engineering/release-and-cicd.md`。

### 8.6 测试与压测

- **负载与并发压测（已定稿）**：**Apache JMeter** 作为 HTTP/API 场景的主工具（脚本、场景、报告；与 CLRP 时期经验延续）。
- **自动化测试（基线）**：单元与集成测试以 **JUnit 5** 等为起点；涉及 PostgreSQL / Kafka 等的集成路径，优先采用 **Testcontainers**（在流水线与工程规范中展开）。
